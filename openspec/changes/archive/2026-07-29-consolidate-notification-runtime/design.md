## Context

`statocysts` 当前由 `index.ts`、`browser.ts` 和 `core/sender.ts` 共同承担通知提供方注册与投递。两个入口重复维护导入、注册列表、单目标 `send()` 和 `createSender()`，而注册表又公开提供方解析能力。新增 Lark、QQ 机器人和 Server 酱时需要同步修改多处，历史上已经出现 Server 酱漏注册，当前也存在注册集合与命名导出不一致。

现有通知提供方通过 `defineProvider()` 统一解析协议、合并专属选项并调用传输实现。各提供方的地址语法校验仍与请求准备绑定。本变更必须保持这些协议和请求行为不变，并避免为了通知器创建时校验而迁移全部提供方。

## Goals / Non-Goals

**Goals:**

- 用一个深通知运行时模块集中目标解析、提供方查找、通知校验、并行分发和错误策略。
- 让服务端与浏览器端各自只有一个内置通知提供方目录，并由该目录同时驱动运行时与顶层命名导出。
- 建立一致的结构化通知接口和通知器行为。
- 通过通知运行时接口测试行为，消除对浅注册表实现的测试耦合。
- 明确并收缩包的公开接口，同时保留具体通知提供方及其专属选项。

**Non-Goals:**

- 不改变任何通知提供方的协议地址语法、请求内容或专属选项。
- 不提前执行提供方专属通知目标校验。
- 不重构网页请求、邮件传输或 QQ 机器人令牌缓存。
- 不提供自动重试、并发上限、取消信号或外部自定义通知提供方注册。
- 不保留旧公开接口兼容适配器。

## Decisions

### 1. 使用结构化通知作为唯一通知表达

公开的通用入口采用 `send(target: string, notification: Notification)`，通知器采用 `send(notification: Notification)`，具体通知提供方继续接受同一个 `Notification`，并可额外接受自身专属选项。

`Notification` 包含必填 `title` 和可选 `body`。共享校验模块 MUST 拒绝非对象通知、非字符串字段以及裁剪后为空的标题，但 MUST 保留原始标题和正文。通知运行时在启动任何投递前校验，`defineProvider()` 也复用该校验，从而保证直接提供方调用与运行时调用一致。

选择对象而不是位置参数，是为了让运行时与提供方共享同一领域表达，并避免未来增加字段时扩张参数列表。

### 2. 通知运行时是唯一通用投递模块

新增内部运行时构建函数，接收某一环境的内置通知提供方集合，并产生该入口使用的 `send()` 与 `createNotifier()`。构建函数不是公开扩展接口，只用于服务端入口、浏览器入口和运行时测试。

顶层 `send()` 通过单目标通知器复用同一投递路径，不单独实现协议解析或错误处理。`createSender()` 被删除并由 `createNotifier()` 取代。`senderRegistry`、`resolveProvider()` 和注册表构建工具不再公开。

选择一个运行时而不是继续让入口直接调用提供方，是为了让所有通用调用共享同一个接口、错误模式和测试表面。

### 3. 静态命名导出文件同时作为提供方目录

建立服务端和浏览器端提供方目录模块。目录模块只包含具体通知提供方的静态命名导出：浏览器目录包含所有浏览器可用提供方，服务端目录复用浏览器目录并增加邮件提供方。

入口模块以模块命名空间读取同一目录中的提供方值来构建运行时，同时使用 `export *` 暴露顶层命名导出。这样新增提供方只需修改对应目录一次，且静态导出仍可被 TypeScript 和打包工具识别。

运行时构建时 MUST 拒绝重复协议。目录测试 MUST 验证预期协议集合，并覆盖当前遗漏的 `serverChan` 与浏览器端 `jsons` 导出。

选择静态目录而不是文件系统扫描或代码生成，是为了保持构建简单，并让服务端与浏览器端差异显式可见。

### 4. 通知器创建只执行通用目标校验

`createNotifier(targets: string[])` MUST：

1. 拒绝空数组。
2. 拒绝非字符串或无法由标准 `URL` 解析器解析的目标。
3. 将目标解析为标准规范化字符串。
4. 拒绝规范化后重复的目标。
5. 按协议查找通知提供方，并拒绝不支持的协议。
6. 缓存规范化目标及对应通知提供方。

提供方专属地址语法仍在实际发送时校验。标准规范化不得擅自改变路径语义，例如不得自行移除末尾斜杠。

完整预解析需要拆分全部提供方的地址解析和通知渲染，范围过大；协议级立即校验已经能消除旧 `createSender()` 静默过滤不支持目标的问题。

### 5. 多目标投递使用无上限并行与聚合失败

通知器发送时同时启动所有目标投递，使用等价于 `Promise.allSettled()` 的行为等待全部目标完成，不保证完成顺序，不自动重试，也不设置并发上限。

全部成功时解析为 `undefined`。存在任一失败时，运行时抛出公开的 `NotificationDeliveryError`。该错误保留每个失败目标及原始原因，并提供成功数和失败数。顶层单目标 `send()` 也包装为该错误；直接调用具体提供方时仍暴露原始错误。

选择等待全部完成而不是首次失败即结束，是因为并行任务无法可靠取消，并且告警投递不应因一个目标失败而阻止其他目标。当前目标列表较小，没有真实需求证明并发调度接缝必要。

### 6. 配置错误与投递错误分离

通知器创建阶段的空列表、无效地址、不支持协议和重复目标统一抛出 `TypeError`。通知对象无效也抛出 `TypeError`。只有已经开始的实际投递失败才产生 `NotificationDeliveryError`。

这样调用错误和运行时失败具有不同且稳定的错误模式，同时避免增加多个低杠杆效应的公开错误类型。

### 7. 不再公开自定义提供方扩展接缝

移除通过包入口公开的 `defineProvider`、`defineTransport`、`buildSenderRegistry`、传输对象和相关核心类型。它们仍可作为包内部实现存在，但调用方不能向内置通知运行时注册自定义提供方。

当前没有文档化扩展模型，也没有两个外部适配器证明该公共接缝真实存在。未来出现真实需求时，应独立设计扩展接口，而不是固化当前内部形状。

### 8. 用运行时行为测试替换注册表实现测试

删除 `core/sender.spec.ts` 中围绕可调用注册表和 `resolveProvider()` 的测试。新增运行时测试，使用内部记录通知提供方覆盖通知校验、创建校验、缓存解析、并行启动、全部等待、聚合错误与成功返回值。

服务端和浏览器端目录分别测试协议集合与命名导出。现有具体通知提供方测试继续保留，并增加共享通知校验的一致性覆盖。

## Risks / Trade-offs

- [公开接口不兼容导致调用方升级失败] → 在变更说明和文档中给出 `send()`、`createNotifier()` 与具体提供方调用的迁移示例，并在同一版本中完成命令行迁移。
- [模块命名空间中意外混入非提供方值] → 目录模块只允许导出通知提供方值；运行时构建时验证对象形状和协议唯一性。
- [无上限并行在异常大目标列表上产生资源峰值] → 保持本次接口简单；出现真实规模需求后再引入内部调度或显式并发策略。
- [通知器创建成功但提供方专属地址仍可能无效] → 文档明确创建阶段只保证通用地址与协议有效；实际投递继续返回原始提供方原因。
- [具体提供方与运行时重复执行通知校验] → 共享同一纯校验函数，运行时提前校验保证全有或全无，提供方校验保证直接调用一致。

## Migration Plan

1. 引入 `Notification`、通知校验和 `NotificationDeliveryError`，暂不切换入口。
2. 建立服务端与浏览器端提供方目录及目录测试。
3. 实现通知运行时和通知器行为测试。
4. 切换服务端、浏览器端和命令行入口到新接口。
5. 更新具体通知提供方共享校验，补充缺失命名导出。
6. 删除旧发送器、公开注册表和核心内部导出，并删除对应测试。
7. 更新 README 与类型声明示例，运行测试、类型检查、构建和发布检查。

回滚需要整体撤销该不兼容版本；不提供同时维护新旧接口的运行时开关。
